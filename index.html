Multi-camera face-recognition attendance system

Industry project, 2026 · Inspirer Technologies · technical write-up of the recognition core

How it works

Each camera runs in its own worker thread. A single shared inference thread takes frames from all of them, finds and aligns each face, turns it into an embedding, and compares that embedding with the people enrolled. If the best match clears the threshold, the person is identified; otherwise the face is treated as unknown.

Detection and recognition both use Apache-2.0 models from the OpenCV Zoo, run through cv2.dnn. I replaced an earlier non-commercial-licensed model (InsightFace buffalo_l) after auditing the licences of the model weights and their training data, accepting a lighter model in exchange for a deployable one.

Benchmark: LFW verification

Standard 6,000-pair, 10-fold protocol. The threshold is chosen on nine folds and scored on the held-out fold. Reproducible with a single script; 0 of 6,000 pairs had no face detected.

Threshold calibration from field failures

Benchmark accuracy did not transfer cleanly to live cameras: people at a distance were misidentified. I recalibrated the matching threshold 0.36 → 0.51 → 0.46, analysing the false-accept versus false-reject trade-off through inter-class and intra-class similarity margins. At the deployed threshold of 0.46 the LFW result is 0 false accepts in 3,000 impostor pairs at a 5.5% false-reject rate. I also compared the lightweight-versus-accuracy trade-off of SFace against ArcFace-class models.

Limits, stated plainly

  • LFW is an easy, near-frontal benchmark with pre-cropped faces. Read the result as "99.1% on LFW", not "99% accurate" in general.
  • SFace is a pretrained OpenCV Zoo model. I evaluated and calibrated it; I did not train it.
  • 0 false accepts in 3,000 pairs bounds the true rate at roughly 0.1% (95% confidence).
  • The real deployment is a handful of people on a few cameras. Larger-scale load tests (37,500 simulated identities, 150 devices) measured the backend, not recognition accuracy.

Tenant isolation

The platform serves several tenants from one database. Isolation is enforced by PostgreSQL itself, not just by application code: each request sets a tenant context, and row-level security policies only let a query see rows that belong to that tenant. Table owners bypass RLS by default, so the application connects as a non-owner role.

What adversarial testing found

I wrote 10 adversarial tests across 8 attack classes (cross-tenant read, write and ID guessing, among others) and ran them against my own system.

Hardening and biometric data

  • Authentication: refresh-token rotation, HttpOnly cookies, breached-password checking, timing-safe login.
  • Operations: backup restore drill, TLS with automated certificates, monitoring alerts.
  • Biometric data: face embeddings are treated as sensitive. Edge and cloud stores are separate, no source images are kept server-side, and test data is synthetic only.

TABEEB: secure, privacy-aware healthcare platform with LLM report analysis

Final Year Project · Runner-up, Projects category, VisioSpark competition

Report analysis pipeline

A pipeline that accepts scanned images, PDFs and text and returns patient-readable summaries flagging values outside reference ranges. The retrieval-augmented design lets the model format only retrieved facts, with labelled estimates as a fallback, and works across model families (Gemini and Gemma), which showed how instruction following varies between models.

I studied prompt design and decoding control in a high-stakes domain (low temperature for factual summaries, higher for conversational Q&A) to find where factual fidelity breaks down, and cut token usage by about 30% with context summarisation.

Access control and authentication

Three roles (patient, doctor, admin) get different levels of assurance. Admins use a separate token channel with TOTP two-factor authentication, and sensitive actions such as creating another admin need an extra step-up check. Doctors are verified against the national medical council registry. Authentication endpoints are rate-limited (10 attempts per 15 minutes) against brute force.

  • Uploads: server-generated signed upload signatures, so clients cannot upload arbitrary files.
  • Real-time: authenticated WebSockets, role-scoped rooms, short-lived signed video tokens.
  • AI security: prompt-injection and jailbreak resistance and output constraints for the LLM, plus an analysis of the privacy risk of sending patient documents to third-party AI APIs.

Open problems I want to work on: faithfulness of LLM summarisation, evaluating output without ground truth, privacy and security of LLM pipelines handling sensitive documents, and low-resource Urdu–English NLP.
